# Kindle 多机型适配调研报告

> 调研时间：2026-10-16 ｜ 方法：FBInk / KOReader / slate 源码 + MobileRead Wiki/论坛 + KOReader issue 真机日志 + 本机 PW1 实测
> 结论均标注「实测」「推断」「未证实」。

## 0. 重大勘误：我们的真机是 Paperwhite 1（2012），不是 PW2

多源交叉验证：

- 固件 5.6.1.1 是 **PW1 的最终版本**；PW2 从 5.4.0 起步
- Yoshime 平台 + `yoshi_battery` + i.MX508 是 PW1 特征；PW2 是 Wario 平台 + `wario_battery` + i.MX6
- 来源：KindleTool kindle_tool.h、MobileRead Kindle_Firmware Wiki、KOReader device.lua

当前应用里机型映射（YOSHIME→PW2）是错的，适配时要改。FBInk 实测 PW1 的 fb 几何（758×1024/8bpp/stride 768）与我们的实测完全一致，屏幕镜像不受影响。

## 2. 对应用六大模块的影响分析

### 2.1 屏幕镜像（差异最大，但有统一的运行时探测方案）

**好消息**：
- 所有黑白机型 stock 都是 **8bpp 灰度**，只有 ColorSoft 是 32bpp 彩色
- 所有机型活跃帧都在 **offset 0**，只有 /dev/fb0 一个 fb
- mxc 时代（PW1~PW4）rotate=3 但内存按逻辑方向存储，直接取字节就是正立图像（我们现有方案通用）

**需要注意的差异**：
1. **stride**：mxc 机型有对齐填充（758→768、1072→1088、1264→1280），MTK 机型 stride==宽（无填充）。必须运行时读，不能算术推导
2. **MTK 双帧（PW5/KT5/PW6/Scribe）**：显存是双倍高度双缓冲，框架可能 pan 到第二帧——**必须读 yoffset**，从 `yoffset×line_length` 处取图，否则读到旧帧（slate 作者踩过的"幽灵画面"坑）。sysfs 拿不到 yoffset，需要设备端 helper（见 §3）
3. **PW6 边距**：fb 1272×1696 > 面板 1264×1680，取图后要裁边（+8/+16）
4. **夜间模式**：全系用 grayscale==2（8bit 反相），镜像要检测并反转
5. **Oasis1/2/3、Scribe 有陀螺仪**：方向随握持变化，横屏时 xres/yres 互换，需定期重读几何
6. **ColorSoft 32bpp**：需要 RGB 解码器（唯一非灰度机型）

**探测数据源（本机已验证）**：
- `/sys/class/graphics/fb0/mode` → `U:758x1024p-0`（可见分辨率，横屏时会变 1024x758）
- `/sys/class/graphics/fb0/virtual_size` + `bits_per_pixel`
- `/usr/sbin/eips -i` → `line_length`（stride）、`smem_len`、驱动 id（mxc_epdc_fb / hwtcon_v2 可判 MTK）
- yoffset：sysfs 无。方案 A：随连接推送一个静态编译的 fbinfo 小工具（读 FBIOGET_VSCREENINFO 打印）；方案 B：打包 FBInk 的 fbdepth 二进制（官方有 ARM Kindle 版，注意 soft/hard-float 双通道）；方案 C：MTK 机型读两帧取与上次画面连续的一帧（heuristic，不推荐）

**成熟工具的做法**（FBInk/KOReader/slate 一致）：全部运行时读 vinfo/fixinfo，**绝不按机型硬编码几何**；机型识别只用于 quirk 分支（MTK？彩屏？陀螺仪？）。

### 2.2 电池（路径各代不同，需 fallback 链）

| 世代 | 路径 | 单位 |
|---|---|---|
| K4/Touch/PW1 | `/sys/devices/system/yoshi_battery/yoshi_battery0/` | %, µV, 0.1°C（我们实测） |
| PW2/Voyage/PW3/OA1 | `/sys/devices/system/wario_battery/wario_battery0/` | 同上(推断) |
| KT3 | `/sys/class/power_supply/bd7181x_bat/` | 标准 power_supply |
| OA2/OA3 | `/sys/class/power_supply/max77796-battery/` | capacity 可能 >100% |
| PW4/KT4 及全部 MTK 机型 | `/sys/class/power_supply/bd71827_bat/` | 标准 µV/0.1°C(推断) |

推荐三级降级（KOReader 同款）：`lipc-get-prop com.lab126.powerd battLevel` → sysfs 候选列表 → `gasgauge-info -c`（K3~PW4 自带，MTK 未证实）。电压/温度单位在各代不统一，建议主要显示百分比+状态。

### 2.3 lipc / 防休眠（零差异，直接沿用）

- lipc 从 FW 5.0 到 5.19 全系存在（含 MTK 新机，KOReader 至今全系使用）
- `preventScreenSaver` 已在 PW3@5.16、PW5@5.16.x 实证有效，MTK 上 KOReader 走同一代码路径
- 电池、设备名等也可走 lipc 属性兜底

### 2.4 性能监控（/proc 全代兼容，仅多核需处理）

- `/proc/stat`、`/proc/[0-9]*/stat`、`/proc/meminfo`、`/proc/loadavg` 从内核 2.6.31 → 4.9 无破坏性变化，仅尾部字段累加（解析器需容忍尾部字段）
- **多核机型**（OA2/OA3 双核；PW5+ MTK 传闻 4 核）：/proc/stat 出现 cpu0..cpuN 段；**进程 CPU% 需按核数归一化**（否则多线程进程会 >100%），核数 = cpuN 段计数
- 我们解析器按最后 `)` 切分 comm 的写法全代安全

### 2.5 进程/线程

与 2.4 同源，无额外差异。注意 MTK 机型进程更多（4 核），UI 列表可考虑虚拟滚动。

### 2.6 文件管理（SFTP）—— 零差异

### 2.7 终端

- 所有机型 root shell 都是 busybox ash，无 bash；无证据任何 stock busybox 编译了 Unicode → `ll` 函数方案全代通用
- busybox 版本 1.17（PW1）→ 1.22+（新固件，具体未证实），别依赖新 applet
- 中文文件名问题在各代一致存在

### 2.8 机型识别

- **`/proc/usid` 序列号前缀是唯一可靠方式**（KOReader 的做法）：B024=PW1、B0D4/B0D5=PW2、G090G1=PW3、G090KB=Voyage、G000PP=PW4、G001LG=PW5、G00227=Scribe 等（完整表在 KOReader device.lua / MR Wiki Kindle Serial Numbers）
- cpuinfo 的 Hardware 字段是 **SoC 名**（i.MX50/i.MX6/i.MX7/MT8110），不是平台代号，只适合辅助判断
- FBInk fbink_device_id.c 有完整"序列号前缀→机型→quirk"表，可直接移植

## 3. SSH 与越狱现状（决定适配的"可达用户面"）

- **越狱现状（2026-10）**：除 2026-10-06 刚发布的 5.20.x 待验证外，**固件 ≤5.19.6 的几乎所有机型都可越狱**（LanguageBreak ≤5.16.2.1.1、WinterBreak <5.18.1、AdBreak 5.18.1-5.18.5、Sanctuary 5.16.4-5.18.3、Véra ≤5.19.6、SpiderCat 5.16.3-5.19.5）。主流停留固件：5.16.2.1.1（LanguageBreak 上限）和 5.19.x（SpiderCat/Véra 用户）
- **SSH 接入全系一致**：USBNetwork（dropbear + root + 端口 22）。差异点：USB 模式设备固定 IP 192.168.15.244；WiFi SSH 默认关需开启；KPM 生态的 dropbear 监听 2222（建议端口探测 22/2222）；root 密码由序列号派生（可在管理器里内置生成器，参考 sven.de/kindle 算法），古董机兜底 fiona/mario
- **ABI 分水岭**：FW 5.16.3 起用户态 hard-float——如果我们往设备推 helper 二进制（如 fbinfo），需要 soft-float（≤5.16.2）和 `_khf` hard-float（≥5.16.3）两个通道
- **生态空档**：调研未发现任何活跃的"跨代多 Kindle 批量管理器"开源项目（KindleMate 只做 USB 剪贴管理；kPM/KUAL 是设备端自管理）——这个工具的定位是空白区

## 4. 建议的适配架构（不写代码，仅方案）

1. **连接时能力探测**（一次 SSH 往返）：/proc/usid → 机型；eips -i + fb0 sysfs → fb 几何 + 驱动 id（判 MTK）；电池路径候选探测；/proc/stat 段数 → 核数。结果缓存为 per-device profile
2. **屏幕镜像参数化**：ScreenService 从 profile 读 {宽,高,stride,bpp,yoffset,驱动}，解码器注册表：8bpp 灰度（全系黑白）+ 32bpp RGB（ColorSoft）；grayscale==2 反相；MTK 双帧读 yoffset；PW6 裁边；Oasis/Scribe 定期重读几何
3. **电池 fallback 链**：lipc → sysfs 候选 → gasgauge-info；统一归一化单位
4. **CPU% 按核数归一化**；解析器容忍尾部字段
5. **设备端 helper（可选但推荐）**：fbinfo 静态小工具（ARM，双 ABI 通道）解决 yoffset；失败则退化到 sysfs 方案（MTK 双帧机型可能偶发读到旧帧）
6. **多设备管理**：连接配置改列表（多台 Kindle），设备识别码用序列号，UI 加设备切换
7. **机型映射表**：修 PW1 勘误 + 按 FBInk 表补全（Yoshime→PW1、Wario→PW2/PW3/Voyage、Rex→PW4、Bellatrix→PW5+）

## 5. 主要未证实项（建议拿到对应真机后验证）

- Scribe / KT6 / ColorSoft 的 fb 几何（无直接真机日志）
- KT2/KT3/KT4 stride=608 为推断
- PW5 4 核的 cpuinfo 直接实证
- MTK 机型 bd71827 节点里 voltage/temp 属性存在性
- 5.20.x 固件越狱可行性
- gasgauge-info 在 MTK 机型上的存在性
